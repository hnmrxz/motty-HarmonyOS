# 许可证与第三方组件（重要：整包分发已按 GPLv3）

**结论（2026-11-10 决定）**：本仓库的分发按 **GPL-3.0-or-later 组合分发**。
上游 Motty 原仓库是 Apache-2.0；从本轮起，**对外分发的整包**（HAP 及其对应源码）
满足 GPLv3 义务。Apache-2.0 的既有文件仍保留其原始声明，但整包不可再用"仅 Apache-2.0"表述。

这是一条**单向决定**：一旦对外分发过 GPLv3 组合，就不能再回到纯 Apache-2.0 分发。

## 为什么必须走到 GPLv3

| 事实 | 影响 |
|---|---|
| 本仓库原许可 Apache-2.0 | Apache-2.0 与 **GPLv3 兼容**、与 **GPLv2 不兼容** |
| LibVNC 许可 **GPL-2.0-or-later** | 可以用 v2 之后的任意版本 → 选 **v3** 才与 Apache-2.0 兼容 |
| LibVNC 官方 FAQ：**链接即衍生作品** | 不能"动态加载规避"，整包受 GPL 约束 |

## 义务清单（分发时必须做到）

1. **提供完整对应源码**：本仓库本身（ArkTS/C++/构建脚本/第三方构建脚本）即为对应源码；
   `harmonyos/native/third_party/src/` 下是第三方源码（不入库，由脚本按版本下载）。
2. **保留版权与许可声明**：`LICENSE`（本项目）、以及每个第三方组件的原始 LICENSE 文件。
3. **下游可再分发**：不得对接收者施加额外限制（例如禁止再分发）。
4. **构建脚本可复现**：`build-thirdparty.ps1` 等脚本必须能重新产出同样的第三方静态库。

## 第三方组件台账

| 组件 | 版本 | 许可证 | 用途 | 是否静态链接 |
|---|---|---|---|---|
| libssh2 | 1.11.1 | BSD-3-Clause | SSH/SFTP/转发 | 是 |
| mbedTLS | 3.6.2 | Apache-2.0 | TLS/加密原语（含 DES） | 是 |
| libvterm | neovim fork | MIT | 终端网格解析 | 是 |
| LibVNC (client) | 见构建脚本 | GPL-2.0-or-later（按 v3 使用） | VNC/RFB 客户端 | 是 |
| zlib | 系统 `libz` | zlib | SFTP/LibVNC 压缩 | 否（系统库） |
| `github.com/pkg/sftp` | 1.13.x | BSD-2-Clause | **仅测试夹具**（不进应用包） | 否 |

> 说明：`tools/design/sshfixture` 是测试夹具，**不随应用分发**，其依赖不影响应用许可。

## 上架相关（需自行复核，不要当成已确认）

- GPL 本身不阻止上架应用市场，但**必须能提供源码**；华为应用市场的具体条款需在上架前逐条核对。
- 若将来要接入**闭源商业 SDK**，会与 GPLv3 冲突，那时必须回到自研 RFB（或移除该 SDK）。
- 自研 RFB 实现**保留在库里**作为回退路径：万一需要回到 Apache-2.0 分发，可移除 LibVNC 编译开关。
